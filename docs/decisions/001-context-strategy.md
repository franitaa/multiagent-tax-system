# 001: Context strategy

Status: accepted. Owner: orchestration (Person 1). Code: `src/orchestration/context.py`, `access.py`.
Numbers below are from `docs/metrics.md` at the time of writing; that file is regenerated by
`python -m scripts.measure_context` and is the source of truth.

## Problem
The graph has six narrow agents, structured outputs, and a session that can be long (a 30-turn
conversation) or wide (many documents). Handing every agent the whole state makes each call pay for
everything that has ever happened, spreads personal data to agents that have no use for it, and
makes behaviour harder to test. The assignment asks for an explicit choice among message trimming,
rolling summarisation and selective recall.

## Options, for this system

| | Message trimming | Rolling summarisation | Selective recall |
|---|---|---|---|
| What it is | Keep the last N messages | A model compresses older context into a summary | Give each agent only the slices of structured state it needs |
| Cost | Nearly free | An extra model call at every roll-over; non-deterministic, so hard to test offline | Needs a view definition per agent (we already have the access policy) |
| Helps with | Chat only | Anything, but lossily | Chat, documents, records, results |
| What it can lose | Anything the user said early and we never wrote down (e.g. "my husband died in March" in turn 3) | Detail and exactness; a summary can drop or distort a flag or a figure | Whatever a view definition wrongly excludes |
| Fit here | Only Intake holds a chat. Most of our volume is documents and records, which trimming cannot touch. A silently dropped statement could hide an escalation condition | A summary that contains an amount has no provenance (breaks rule 3), is not the evidence an auditor wants, and copies personal data into free text | State is typed, so "relevant" is a lookup, not a guess. Matches narrow agents with structured outputs |

## Decision
**Selective recall as the backbone, plus a deterministic rolling summary of decisions, plus a chat
window for Intake only.**

1. **Scoped views.** Each agent's view is its read allow-list narrowed further: Extraction gets
   exactly one document; Rules gets facts and typed records; Computation gets numeric facts and the
   filing status; Review gets the assembled return; the orchestrator gets flags and counts. Escalation
   and human decisions are in every view, so a safety signal is never scoped away.
2. **Rolling summary, templated not generated.** The orchestrator rebuilds `session_summary` at
   every visit from milestones, counts and condition codes ("documents extracted 12/12; review
   revision rounds: 1; human: FILING_STATUS_AMBIGUITY=continue"). It never contains amounts, chat text
   or names, is bounded (last 5 human decisions), and costs no model call. An LLM summariser can
   replace it later without changing the contract.
3. **Window for Intake only.** Last 6 messages. Older statements are recalled through `facts`, which
   are structured, sourced and lossless.
4. **Switchable.** `--no-context-strategy` (`build_graph(context_strategy=False)`) gives every agent
   the full state. Both modes run the same scenario and must reach the same outcome (tested).

### Where I challenged the starting recommendation
I looked for a better fit and did not find one, but two refinements matter. First, the three options
are not alternatives here: scoped views *are* selective recall, and trimming is still the right tool
for the one place that holds raw chat. Second, the summary must hold decisions and flags, never
figures: dollar amounts stay in `computed` with a `ProvenanceRecord`, otherwise the summary becomes
an unsourced dollar amount.

### Risks we accept, and the mitigation
- **A view hides something an agent needed.** Mitigation: views are changed only through `POLICY`
  and `TRANSFORMS` in code review, and `test_context_views.py` pins each view.
- **Intake's window drops something that matters.** Mitigation (a rule in the contract): anything
  Intake must remember goes into `facts`; the window is not memory.
- **Facts accumulate.** Measured below: the scoped curve is flatter, not flat. Retrieving only the
  facts relevant to the current question is the next step and is not built.
- **Numeric-only facts for Computation could hide a string it needs.** It can ask for a wider view
  through a `POLICY` change; the filing status already arrives via `eligibility`.

## The orchestrator's view is bounded and model-safe
The orchestrator is deterministic Python (the router plus the loop guard), not a model. Its routing
view holds flags and counts only: at most the last 3 handoffs as `{step, to, reason}` (reason cut to
60 characters), `n_docs_pending` instead of id lists, the escalation *condition code* (not its text).
It cannot see which documents are pending and does not need to: the extraction fan-out reads the
document list from graph state, not from the orchestrator's view.

Two things its code needs would bloat a model-facing view and are useless to a model: the loop
guard's fingerprint history (up to 24 hashes) and a failed review's findings (copied, uninterpreted,
into the revision request). They travel on a separate `control` channel (`View.control`,
`context.control_view`): not a key of the view, so not token-counted, and listed separately in the
trace (`control_fields_read`). If the orchestrator ever becomes model-driven it should be given only
the routing view, which already carries everything a routing decision needs.

Measured (estimated tokens per orchestrator visit): unbounded view 83 to 223 and rising; bounded
78 to 146; with guard and review data in the view 115 to about 240; with the control channel 106 to
174 on the short clean and review-loop runs, and 111 to 180 in the 30-turn, 12-document session of
`metrics.md` (the last few tokens are the document count and the summary). Independent of the number
of turns and documents. Tests:
`test_orchestrator_view_is_bounded`, `test_orchestrator_view_excludes_deterministic_only_inputs`.

## Privacy effect
Smaller views also mean fewer agents see raw material. Raw document text: Extraction only, one
document per worker. Raw chat: Intake only, last 6 messages. Review and Computation see structured
values and provenance, not text. Traces record field *names*, never values. The summary holds no
free text.

## Results (30 turns, 12 documents, one revision round; estimates, see metrics.md)
| | Strategy on | Strategy off |
|---|---|---|
| Total input tokens, all model calls | 33,736 | 618,693 (18.3x) |
| Intake input, turn 1 to turn 30 | 88 to 1,047 | 12,190 to 17,613 |
| Intake growth per turn | 29 tokens | 186 tokens (6.5x) |

Caveats, also stated in `metrics.md`: counts are `ceil(len/4)` estimates of the view each agent was
handed (agents are stubs, no model usage exists); most of the total ratio is raw document text
carried in the full state from the first call, so the per-turn growth is the fairer curve-shape
number; the scoped curve is flatter but not flat.
